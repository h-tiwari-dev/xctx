# Milestone 4: Branching agents and competing attempts

**Status:** Wave 1 is done and merged into `m4-base`: `xctx-core` attempts, `xctx-attempt`, the attempt methods and the Inbox gate. The non-UI half of Wave 3 is on `m4-app-core`; see [Wave 3 (app core) status](#wave-3-app-core-status). The attempt UI is next.

Milestone 4 lets a space **git-branch a whole agent**: its code, its `pi` session and its scratch state. Several
attempts at the same problem (Solutions 1, 2, 3) run side by side, each in its own hidden worktree. The user compares
their **outcomes** (repro, tests, diff, the agent's own summary) on a review sheet, discards the dead ends, and adopts
the winner back into the space.

## What a user can do at the end of it

1. **Fork attempts from a running writer agent** (graph panel, a space tab action, or `⌘⇧F`):
   - Choose how many attempts (2 to 4), and optionally give each its own instruction, for example "Solution 2: use a
     token bucket instead of a sliding window".
   - For each attempt, xctx:
     - snapshots the writer's worktree, uncommitted changes included, without touching it (`git stash create`);
     - makes a hidden worktree on `space/<slug>/attempt-<n>` from that snapshot;
     - writes the attempt's own `mise.<slug>.toml` with a fresh `PORT`;
     - copies the space's scratch folder to `/tmp/xctx-scratch/<slug>/attempts/<n>/`;
     - starts `pi --fork <the writer's session>` in the new worktree, so the attempt starts from everything the
       agent knew, with its instruction as the first message.
   - Forking is the user's action. An agent can only *propose* attempts (`attempt.propose`), and the proposal is a
     Plan Gate, because it adds agents and worktrees.
2. **Watch attempts run in parallel**: an attempt strip in the space tab shows each attempt's state (running, done,
   failed, discarded) and switches the panes to that attempt. Each attempt's agent reports its outcome over the socket
   (`attempt.report`: summary, tests run and passed, repro status), and xctx adds the diff against the fork point.
3. **Compare and decide on a review sheet** (`⌘⇧R` or when every attempt is done):
   - One column per attempt: the agent's summary, tests (passed/failed/not run), repro status, a diffstat and a
     changed-files list, with each file's diff a click away. Secrets are masked with `xctx_core::Redactor`.
   - **Discard** an attempt: its agent stops, and its worktree, branch, mise file and scratch folder are removed.
   - **Adopt** the winner:
     - It is merged into `space/<slug>`: a fast-forward when the space branch has not moved since the fork, else a
       merge commit. xctx checks for conflicts first (`git merge-tree`) and refuses with the conflicting files listed
       rather than leaving a half-merged worktree.
     - The writer pane continues from the winning session (`pi --session <winner>`).
     - The other attempts are offered for discard.
   - Adopting is never available on the control socket.
4. **Keep the session tree**: the space remembers which session each attempt forked from and which one was adopted
   (`attempts.json`), so the graph panel can show the lineage, and Ship or Discard of the space cleans up every
   attempt.

## Not in this milestone

- An automatic judge that picks a winner. The user decides; agents may only post findings.
- Forking across machines or into cloud runtimes.
- Attempts of more than one writer at once. Fork one writer; the rest of the graph is shared.
- Non-terminal plugin panes (Milestone 5).

## Decisions (settled in Wave 1)

- **Sessions: ids, not folders.** xctx names every agent's `pi` session itself and starts agents with
  `pi --session-id <id>`, which opens that session in the current directory or creates it. An attempt is
  `pi --fork <source id> --session-id <attempt id>`, run in the attempt's worktree. This was checked with pi 1.6: the
  fork, run from another directory, found its source by id, kept its context, and recorded the source file as
  `parentSession` in its header. That header is the lineage. pi's session storage stays where it is. The ids are
  `xctx-<slug>-<agent>` and `xctx-<slug>-<agent>-attempt-<n>` (`xctx_core::pi_session`). Agents that started before
  this change have no id; Wave 3 must give them one, or fork them from the newest session in their worktree's folder.
- **Branches.** Attempts are on `attempt/<slug>/<n>`. They cannot be under `space/<slug>/`, because git cannot have
  both a branch `space/<slug>` and branches below it. Worktrees go next to the space's, as `<slug>--attempt-<n>`.
- **Snapshot.** `git::snapshot_commit` stages the whole worktree into a temporary index. Uncommitted changes and
  untracked files are included, ignored files (the space's mise file among them) are not, and neither the
  worktree nor its index changes. All attempts of one fork share that commit.
- **Adopting.**
  - xctx refuses, changing nothing, when the space's worktree no longer matches the fork snapshot, since the writer
    kept working and that work would be lost. It also refuses when `git merge-tree` finds a conflict.
  - Otherwise the space's uncommitted work, which the attempt already has, is stashed. Then the attempt is merged:
    a fast-forward when it can be. The stash is dropped afterwards, or restored if the merge fails.
- **Limits and ports.** At most 4 attempts per fork (`MAX_ATTEMPTS`). Each attempt takes its own `PORT`, which the
  caller allocates from the space range, avoiding the ports of spaces and of other attempts.
- **Ship and discard.** `xctx-core` does not know about attempt records, so refusing to ship or discard while
  attempts run, and cleaning them up afterwards, is done where the records are (Wave 3).

## Crates

Existing crates stay. Milestone 4 adds one UI-free crate:

| Crate | GPUI | Owns |
| --- | --- | --- |
| `xctx-attempt` | no | `AttemptId`, `Attempt` (fork point commit, branch, worktrees, port, source and forked session, instruction, state `Running` / `Done` / `Failed` / `Discarded` / `Adopted`), `AttemptSet` per space with its invariants (at most 4 live, at most one adopted), `Outcome` (summary, tests, repro, diffstat, files), the comparison model the review sheet draws, and atomic persistence in `<data dir>/spaces/<slug>/attempts.json` |

Existing crates extended:
- `xctx-core` (done in Wave 1):
  - git helpers: `snapshot_commit`, `tree_of`, `diff_stat` and `diff_file`, and `merge_conflicts`
    (`git merge-tree --write-tree`).
  - `attempt::{fork_attempts, discard_attempt, adopt_attempt, attempt_changes, attempt_tip}`.
  - `pi_session`: session ids, the `--session-id` and `--fork` arguments, and finding session files and their
    lineage.
- `xctx-channel`: copy a space's scratch folder into an attempt's (Wave 3).
- `xctx-control` (done in Wave 1): `attempt.list` and `attempt.diff` (read), and `attempt.report` and
  `attempt.propose` (propose). `xctx-ctl` takes `attempt=` for `attempt.report` from `$XCTX_ATTEMPT_ID`.
  `instructions` are passed as JSON, because they may contain commas. No method forks, adopts or discards.
- `xctx-inbox` (done in Wave 1): the `AttemptProposal` gate, which can only be approved or rejected and asks for 1
  to 4 attempts. The notice when every attempt of a fork is done comes in Wave 3.
- `xctx-ui`: `ForkDialog` (count and instructions), `AttemptStrip`, and `ReviewSheet` (columns, per-file diff view,
  Discard and Adopt), with headless GPUI render tests.
- `xctx`:
  - fork from the graph panel and the space tab, and spawn each attempt's panes;
  - switch panes between attempts;
  - collect outcomes and open the review sheet;
  - run adopt and discard as background jobs, the way ship and discard are run now;
  - export `XCTX_ATTEMPT_ID` to attempt panes;
  - show the session lineage in the graph panel.

## Waves

Same workflow as before: branches off `m4-base`, one writer per worktree, and `mise run ci` passing before every
commit.

1. **Wave 1, foundations, in parallel:**
   - `m4-attempt`: `crates/xctx-attempt` (model, invariants, outcomes, comparison, persistence, temp-dir tests).
   - `m4-core`: the git helpers and `fork_attempts` / `discard_attempt` / `adopt` in `xctx-core`, tested on temporary
     repositories, conflicts included. Also settles the session-location decision above.
   - `m4-control`: attempt methods in `xctx-control`, plus the `AttemptProposal` kind in `xctx-inbox`.
2. **Wave 2, UI:** `m4-ui`: `ForkDialog`, `AttemptStrip` and `ReviewSheet` in `xctx-ui`, with render tests.
3. **Wave 3, integration:** `m4-app`: everything wired into `crates/xctx`, including the session-dir change for new
   spaces and the scratch copy.
4. **Wave 4, review and dogfood:** run the parallel reviewer swarm (see `docs/reviews/m2-wave4/reviewer-prompt.md`)
   across `xctx-attempt`/`xctx-core`, `xctx-control`/`xctx-inbox`, and `xctx-ui`/`xctx`, then fix its findings. Then
   dogfood: fork three attempts at a real bug in a scratch repo, compare them on the review sheet, adopt one, and
   check that nothing is left behind (worktrees, branches, mise files, scratch folders, ports).

## Wave 3 (app core) status

Done on `m4-app-core` (`mise run ci` passes), with nothing drawn yet:
- **Session ids.** Every agent pane bound to a graph agent runs a named `pi` session (`crates/xctx/src/agent_session.rs`).
  The id is recorded on the agent's graph node, in a new `AgentNode::session` field in `graph.json` (optional, so old
  files load). A new agent (a launch, a new lane) starts with `pi --session-id xctx-<slug>-<agent>` and records it.
  An agent with an id opens it. An agent from before this change, when resumed, has the newest session pi keeps for
  its worktree forked into its id (`pi --fork <file> --session-id <id>`), so it keeps its conversation. When no such
  session is found, it keeps `pi --continue` and records nothing. Panes bound to no agent behave as before.
- **Attempts in the workspace.** `Workspace::attempts` (`SpaceAttempts`, `attempts.rs`) loads each space's
  `attempts.json` on first use and keeps a change only once it is saved. Attempt terminals live in
  `SpaceTab::attempt_terminals` (number to `PaneTerminal`), not in the layout. They start when a fork records its
  attempts, and again when the space is opened. Attempts run `pi --fork <writer session> --session-id <attempt session>`
  with the instruction as the first message the first time, and their own session afterwards (whether it has started
  is read from pi's folder for the attempt's worktree). Each runs in its worktree with `XCTX_ATTEMPT_ID`, its `PORT`
  and `XCTX_SCRATCH_DIR`. Other panes get `XCTX_ATTEMPT_ID` set empty.
- **Fork, adopt and discard jobs** (`attempt_jobs.rs`), one at a time per space (`Workspace::attempt_jobs`). Quitting
  and closing the window wait for them.
  - Fork takes the store while it runs, so no launch takes a port meanwhile. Its ports avoid active spaces and every
    space's live attempts.
  - Adopt merges first. On a refusal (`ChangedSinceFork`, `AdoptConflicts`) the error is shown as `xctx-core` words
    it, and nothing else changes. Then the attempt is marked adopted, its agent is stopped and its worktree removed.
  - **Writer after adopt:** the writer's id becomes `xctx-<slug>-<agent>-adopted-<n>`, forked from the winning
    session the first time it starts in the space's worktree. Its pane restarts in it now when the tab is open, or
    the next time it opens.
  - Discard stops the attempt's agent, waits for it to exit, removes it and marks it discarded. When the removal
    fails, the agent is started again.
- **Scratch copy:** at fork time, the space's scratch artifacts are copied into `<space scratch>/attempts/<n>/` (the
  `attempts` folder itself is skipped). This uses `ScratchDir` in the app, so `xctx-channel` did not change. It is
  removed with the attempt, and with the space.
- **Control.**
  - `attempt.list` and `attempt.diff` wait for the startup mise check and are masked. `attempt.diff` runs git in the
    background.
  - `attempt.report` saves the outcome. When it finishes a round, it posts the Inbox notice "All attempts of round N
    in `<space>` are done; review them".
  - `attempt.propose` checks the agent (a writer), the count (1 to 4), the instructions (no more than the count) and
    the live-attempt limit, then posts the `FORK` gate. Approving it in the Inbox forks, and marks the item approved
    once the fork succeeded.
- **Ship and Discard of a space are refused** while it has live attempts, or while an attempt job runs. The message
  tells the user to adopt or discard them first. This is checked when the dialog opens and again when it is
  confirmed.

What the attempt UI calls (all on `Workspace`, `crates/xctx/src/attempt_jobs.rs`):
- `fork_attempts(&SpaceId, &AgentNodeId, Vec<Option<String>>, window, cx) -> bool` (the fork dialog; one entry per
  attempt), or `fork_attempts_then(..., done: FnOnce(&mut Workspace, bool, &mut Context))`;
- `adopt_attempt(&SpaceId, number, window, cx) -> bool` and `discard_attempt(&SpaceId, number, window, cx) -> bool`
  (the review sheet);
- `attempt_set(&SpaceId) -> Result<&AttemptSet, String>`, the records for the strip, and for
  `xctx_attempt::comparison` (changed files: `xctx_core::attempt::attempt_changes`, off the UI thread);
- `attempt_terminal(&SpaceId, number) -> Option<Entity<TerminalView>>`, the terminal to show when the strip switches
  to an attempt;
- `attempt_jobs.contains(&SpaceId)`, to draw the buttons busy.

They carry `#[allow(dead_code)]` until the UI calls them. Take it off then.

Left open or risky:
- A launch's port (`Store::allocate_port` in `xctx-core`) does not avoid attempt ports yet.
- Adopt does not stop the attempt's agent before taking its snapshot, so work it writes during the merge is lost.
- The checks for whether a session has started read pi's default layout: `~/.pi/agent/sessions/--<cwd>--/`, or the
  flat `$PI_CODING_AGENT_SESSION_DIR`. With a `sessionDir` set in pi's settings they find nothing. Old agents then
  keep `--continue`, and attempts fork again each time they reopen.
- A lane removed and added again under the same id would reopen the old lane's session.
- The session lineage in the graph panel, and the strip, fork dialog and review sheet, are the UI half.
