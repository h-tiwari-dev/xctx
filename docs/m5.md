# Milestone 5: Plugins and connectors as live panes and agent tools

**Status:** In progress. Waves 1 and 2 are merged; the core of Wave 3 (`m5-app-core`) is done, its panes are next.

A space should not be locked to text and a terminal. Milestone 5 adds **plugins**. Every plugin brings three things:
- a **pane** the user can see;
- **tools** agents can call without anyone watching;
- **events** that can start or stop a space's loop.

The Parent Agent mounts the plugins a task calls for: an API client for an API change, logs and a repro for a bug, a
read-only database for a data change, Jira when the task names a ticket. The user can mount and unmount any of them
too. Connectors (Jira, Figma) have the same shape, pointed at an outside service.

## What a user can do at the end of it

1. **Mount a plugin into a space** from a Plugins menu in the space tab (`⌘⇧P`), or let the Parent Agent do it
   (`xctx-ctl plugin.mount`). Its pane joins the layout like any other pane: it can be split, zoomed and closed, and
   it survives a reshape and a restart. Unmount closes its pane and its tools.
2. **Use the first-party plugins:**
   - **Terminal:** any command in a pane, for example `lazydocker`, `k9s` or `tail -f`. Tool: `shell.run`, which runs
     a one-off command in the space's worktree with its `MISE_ENV` and `PORT`, with a timeout and capped output.
   - **API client:** request, response and history in one pane. Tools: `http.send`, `http.replay` and `http.diff`.
     Events: `response.status` (for example any 5xx) and `response.slow`. It only sends to the space's own
     environment, never `MISE_ENV=production` unless the space was widened to production.
   - **Logs:** tails a command or file, with filtering and level colouring. Tool: `logs.query` (lines matching a
     pattern or level, in a time window). Event: `logs.error` when the error rate crosses a threshold.
   - **Database (read-only):** run a query and see a table. Tool: `sql.read`, through `sqlite3 -readonly` or `psql`
     with `default_transaction_read_only=on`. A write (`sql.write`) is a gate in the Inbox and runs only when the
     user approves it.
   - **Browser:** a page of the space's app (`localhost:$PORT`) with its screenshot, console and network errors.
     Tools: `page.open`, `page.screenshot` and `page.console`. See the browser decision below.
   - **Jira and Figma connectors:** `issue.read`, `issue.comment`, `frame.read` and `frame.export`. Tokens come from
     mise secrets (masked as always). Comments and other writes go through the Inbox.
3. **Write their own plugin** as a manifest (`plugin.toml`). It describes the pane (a terminal command, or a
   first-party renderer such as logs or http), the tools (commands with typed parameters, each read or write),
   the events (a line pattern or JSON a tool prints), and the environments it may touch. User plugins live in
   `~/.config/xctx/plugins/<name>/plugin.toml`. A repo's own plugins (`.xctx/plugins/`) need approval in the Inbox
   the first time, the same way mise needs trust.
4. **Let plugin events steer the loop:** a manifest maps an event to a loop action: `fail` (stop the loop at its
   stage), `pass` (the stage's check passed, so an *until checks pass* loop moves on) or `notice` (post to the
   Inbox). Events land in the shared space as findings, so agents and the review see them.
5. **Pick the agent runner per space or per lane**: `pi`, or any runner described by a runner manifest (command,
   how to give a task, how to resume, how to fork a session). Attempts (Milestone 4) are only offered for runners
   that can fork.

## Not in this milestone

- Plugins running code inside the xctx process. Plugin tools are separate processes, and plugin panes use the
  first-party renderers or a terminal. In-process extensions may come later.
- A plugin marketplace or remote install. Plugins are folders on disk.
- Writes to production from any plugin. A space only reaches production after a widening approval (Milestone 3),
  and even then each write tool asks in the Inbox.

## Decisions (settle in Wave 1)

- **Manifest format:** TOML (`plugin.toml`), read with the `toml` crate (MIT/Apache-2.0). Fields:
  - `name`, `version`, `description`;
  - `[pane]`: `kind = terminal | http | logs | sql | web`, plus that kind's settings;
  - `[[tools]]`: `name`, `description`, `effect = read | write`, `params` (name, type, required, description),
    and either `run = [argv...]` with `{param}` placeholders or `builtin = "<name>"`;
  - `[[events]]`: `name`, `match` (a line regex or a JSON field) and `action = fail | pass | notice`;
  - `scope`: which `MISE_ENV`s it may run under;
  - `secrets`: the env names it needs.

  Tools are run **without a shell**: placeholders fill whole argv elements only. They have a timeout and capped
  output, and their output is masked with the space's `Redactor`.
- **Pane identity:** `PaneKind` (in `xctx-layout`) gains `Plugin`, and `PaneRole` gains `plugin: Option<String>`,
  which defaults to absent so saved layouts still load. Reshape keeps plugin panes the way it keeps agents. This
  avoids making `PaneKind` non-`Copy`.
- **Browser:** GPUI has no webview, and embedding a native `WKWebView` in a GPUI window is a risky native-code
  change. For Milestone 5 the browser plugin drives a real Chrome or Chromium through the DevTools protocol
  (`--remote-debugging-port`, a small CDP client over a websocket crate under MIT/Apache) and shows its
  screenshot, console and network errors in the pane, refreshed on navigation. The page itself opens in a normal
  browser window the user can use. An embedded webview is a follow-up, if it is worth it.
- **HTTP:** the API client uses a small blocking HTTP client crate under a permissive licence (for example `ureq`,
  MIT/Apache) from a background thread. No async runtime is added.
- **Databases:** through their command-line tools (`sqlite3`, `psql`), not driver crates. Read-only is enforced by
  the tool's flags; the read-only check on SQL text is only a second guard.
- **Capabilities on the socket:**
  - `plugin.list` and `plugin.tools`: Read.
  - `plugin.mount` and `plugin.unmount`: Layout. Mounting a connector with write tools, or a repo plugin not yet
    trusted, posts an Inbox gate instead.
  - `plugin.call`: Propose for read tools. Write tools always become an Inbox gate, which the user approves.
  - `plugin.emit`, for an event from a plugin's own tool: Propose.

  Nothing on the socket approves.

## Crates

| Crate | GPUI | Owns |
| --- | --- | --- |
| `xctx-plugin` | no | Manifests (parse, validate, built-in manifests for the first-party plugins), the registry (built-in, user and repo plugins, repo trust), the tool runner (argv templating without a shell, timeouts, output caps, masking, scope checks against `MISE_ENV`), event matching, and the mapping from events to loop actions |
| `xctx-http` | no | The API client core: requests, responses, history per space (`<data dir>/spaces/<slug>/http.json`), replay and diff, and the status and slow-response events |
| `xctx-browser` | no | A minimal Chrome DevTools protocol client: start or attach to Chrome, open a page, take a screenshot, collect console and network errors |
| `xctx-plugin-view` | yes | The plugin panes: `HttpPaneView`, `LogsPaneView`, `SqlPaneView` and `BrowserPaneView` |

Existing crates extended:
- `xctx-layout`: the `PaneKind::Plugin` variant and `PaneRole::plugin`; reshape keeps plugin panes.
- `xctx-control`: `plugin.list`, `plugin.tools`, `plugin.mount`, `plugin.unmount`, `plugin.call` and `plugin.emit`,
  with `xctx-ctl` support.
- `xctx-inbox`: a `PluginGate` kind, for a write tool call, a connector mount or repo-plugin trust.
- `xctx-graph`: loop actions from plugin events.
- `xctx-ui`: the Plugins menu, and a plugin pane header badge.
- `xctx`:
  - mount and unmount; start plugin panes; run tool calls in the background;
  - gate writes through the Inbox; route events to the loop and the shared space;
  - tell the Parent Agent which plugins exist and when to mount them;
  - choose agent runners.

## Waves

Same workflow as before: branches off `m5-base`, one writer per worktree, `mise run ci` passing before every commit.
Large waves run as parallel subagents with disjoint scopes.

1. **Wave 1, foundations, in parallel:**
   - `m5-plugin`: `crates/xctx-plugin`, with tests on temporary folders and fake tools (scripts).
   - `m5-http`: `crates/xctx-http`, tested against a local test server started in the test.
   - `m5-layout-control`: `PaneKind::Plugin` and `PaneRole::plugin` in `xctx-layout` (saved layouts still load);
     the plugin methods in `xctx-control`; `PluginGate` in `xctx-inbox`.
2. **Wave 2, panes and browser, in parallel:**
   - `m5-view`: `crates/xctx-plugin-view` and the Plugins menu in `xctx-ui`, with render tests.
   - `m5-browser`: `crates/xctx-browser`, tested against a local Chrome only when one is installed. Tests skip with a
     message, and never fail, when there is none.
3. **Wave 3, integration, in parallel where scopes allow:**
   - `m5-app`: mount and unmount, plugin panes, tool calls, the write gate, events to the loop, and the Parent Agent
     prompt.
   - `m5-connectors`: the Jira and Figma connectors, tested against a local mock server.
   - `m5-runners`: runner manifests, and `pi` expressed as one.
4. **Wave 4, review and dogfood:**
   - Run the reviewer swarm, one reviewer per area, and fix its findings.
   - Dogfood in a real window, the way Milestone 4 was (AppleScript keys, CoreGraphics clicks, `xctx-ctl`):
     1. mount the API client and logs into a scratch space;
     2. have an agent probe an endpoint with `http.replay`;
     3. check that a `response.status` event fails the loop and a passing probe moves it on;
     4. check that a database write waits in the Inbox.

## Wave 3 (app core) status

Branch `m5-app-core`: plugins are wired into the app's logic. The plugin panes and the Plugins menu are not drawn
yet; the pane worker builds them on the API below.

### Where things are

- `crates/xctx/src/plugin_host.rs` (no GPUI, tested directly): folders, trust, mounts, registries per space, call
  context, tool and built-in execution (`CallJob::run`), events to the loop, control summaries, pane data types.
- `crates/xctx/src/plugin_backend.rs` (no GPUI): the logs tail (a command or a file into a bounded `LogBuffer`,
  with the manifest's events matched on every line) and the per-space Chrome (`BrowserHandle`).
- `crates/xctx/src/plugin_jobs.rs`: the `Workspace` side: mount and unmount, starting plugin panes, background
  calls, gates and their approval, events, runners, and the pane API.
- `crates/xctx/src/plugin_tests.rs`: end to end without a window: a user plugin whose tool is a shell script,
  `http.send`/`http.replay` against a local test server, `sql.read` and a gated `sql.write` on a temporary
  sqlite database, repo trust, mounts across a restart, a logs tail and `logs.query`, and events reaching the
  loop, the shared space and the Inbox. No network, no Chrome.

### Decisions

- **Folders.** User plugins: `$XCTX_PLUGIN_DIR`, else `~/.config/xctx/plugins`. User runners: `$XCTX_RUNNER_DIR`,
  else `~/.config/xctx/runners`. Repo plugins are read from each space repo's **worktree** (`.xctx/plugins/`), so
  a space sees its branch's plugins.
- **Registry per space.** Every request builds the space's registry (built-in + user + its repos'); names clash
  across all three and clashes and bad manifests are shown once in the status bar. Requests without a space use
  built-in + user only.
- **Trust.** `<data dir>/plugin-trust.json` records `{repo checkout, plugin, sha256 of plugin.toml}`. Trust holds
  in every space of the repo; any edit to the manifest asks again. Approving a `TrustRepoPlugin` gate records it
  and, when a mount asked for it, mounts.
- **Mount gates.** A *connector with writes* is a manifest that declares `secrets` and has a write tool (built-in:
  `jira`). `plugin.mount` from an agent posts a `Mount` gate for it; the user mounting from the Plugins menu
  (`from_agent = false`) does not. Untrusted repo plugins always post `TrustRepoPlugin`.
- **Mounts.** One entry per plugin pane in `<data dir>/spaces/<slug>/plugins.json`
  (`{pane, plugin, repo, settings}`), reconciled with the saved layout whenever the space opens (the layout is the
  truth; reshape keeps plugin panes). `MountSettings` override the manifest's pane settings: `command` (terminal
  or logs), `log_file`, `engine` and `database`, `base_url`, `url`. New plugin panes split the focused pane.
- **Backends.** Terminal plugins run `pane_argv` (or `settings.command`) in a terminal, no shell, in the repo's
  worktree with the space env and the panes' `PATH`; none means the login shell. Logs run their command (own
  process group, killed on unmount, space close and quit) or poll their file every 300 ms into a 10 000-line
  buffer; lines are masked on the way in and again when read. http, sql and web start nothing. Chrome starts on
  the first page action, **not headless** (the page opens in a real window the user can use), with its profile in
  `<data dir>/browser-profiles/<slug>/`; it quits when the last web pane of the space is unmounted, the space
  closes, or xctx quits (skipped at quit if a page action holds it at that moment).
- **Calls.** `plan_call` with a context from the space: the mount's repo worktree (else the first repo), `PORT`,
  effective `MISE_ENV`, the production flag, and only the secrets the manifest declares, taken from the secrets
  the space's mise check found (`EnvReport.secrets`; plain, non-redacted mise values are not known to xctx, so a
  manifest needing one fails with a missing-secret error). Tools get the panes' `PATH`. Tool runs: 60 s, 256 KiB.
  `http.*` go to `xctx-http` (allowed hosts: local + the pane's base URL host; history saved per space),
  `page.*` to the space's browser, the rest to `xctx_connectors::run_builtin`. Output: the JSON a tool printed,
  else its text (with `[stderr]`, `[exit N]`, `[timed out]` notes), masked. `plugin.call` waits for the startup
  mise check like the other masked reads.
- **Writes.** A write tool not yet approved posts `PluginGate::WriteCall` with its arguments as masked compact JSON
  (cut at 4000 characters) and the `reason` argument as rationale. The real arguments are kept in memory by gate;
  after a restart they are recovered from the gate only when nothing in them was masked or cut. Approving runs the
  call with `approved: true`, settles the gate, and posts the result as an Inbox notice and a finding.
  Rejecting just settles it.
- **Events.** From tool output lines (`match_events`), built-in events (`response.status`, `response.slow`,
  `logs.error`), tailed lines, and `plugin.emit` (the event must be declared and the plugin mounted). Each
  becomes a finding by `plugin:<name>` (error for fail, warning for notice, info for pass). `fail` blocks a loop
  that is running, awaiting approval or out of budget (`LoopRun::block`, it resumes at the same stage); `pass`
  advances a *running* loop as `loop.advance checks_passed=true` does (an ask-each-step loop then waits and gets
  the usual approval notice); `notice` and `fail` post an Inbox notice. Identical events (space, plugin, event,
  detail) within 5 s are dropped; events from tails are also limited to one per event per 5 s whatever the line.
- **Runners.** Agent panes build their arguments with `build_args` (`pi` by default; `pane_launch_with` keeps its
  signature and its tests, and a test checks `pi`'s runner gives exactly `agent_args` for every start and
  session). The runner is chosen per lane (`AgentNode::runner`) or per space (`SpaceGraphDocument::runner`), both
  optional and absent from saved JSON when unset. A runner without named sessions runs an unnamed one (and its id is
  not recorded); a `stdin` task is typed into the terminal. Forking attempts is refused with the runner's own
  "cannot fork sessions" message, both when approving and when an agent proposes.
- **Parent Agent.** Its prompt lists which plugin to mount for which task and the `plugin.*` commands.

### API for the pane worker (all on `Workspace`, `crates/xctx/src/plugin_jobs.rs`)

Menu and mounting:
- `plugin_menu_entries(&self, space: &Space) -> Vec<PluginSummary>`: what the space can mount.
- `mounted_plugins(&mut self, id) -> Vec<MountedPlugin>` (`pane`, `plugin`, `repo`, `kind` =
  `terminal|http|logs|sql|web`, `settings`).
- `mount_plugin(&mut self, id, plugin, repo: Option<String>, settings: MountSettings, from_agent: bool, window,
  cx) -> Result<MountOutcome /* Mounted(PaneId) | Gated(ItemId) */, RpcError>`; use `from_agent = false`.
- `unmount_plugin(&mut self, id, UnmountTarget::Plugin(name) | UnmountTarget::Pane(pane), window, cx) ->
  Result<Vec<PaneId>, RpcError>`. Closing a plugin pane with ⌘W unmounts it too.
- `set_runner(&mut self, id, agent: Option<&str>, runner: Option<&str>) -> Result<(), String>`; the runners are
  `self.runners` (`RunnerRegistry`).

Pane data (read in render; all text already masked):
- `plugin_http(&mut self, id) -> HttpPaneData { base_url, history: Vec<Exchange>, selected, diff, busy, error }`.
- `plugin_logs(&self, id, pane) -> Option<LogsPaneData { source, lines: Vec<LogLine>, status: TailStatus }>`.
- `plugin_sql(&mut self, id, pane) -> SqlPaneData { engine, database, result: Option<SqlTable { columns, rows,
  row_count, truncated }>, error, busy, write_pending }`.
- `plugin_browser(&self, id) -> BrowserSnapshot { phase: BrowserPhase, url, screenshot: Option<Arc<Vec<u8>>>,
  screenshot_generation, console, network_errors, error }` (rebuild the image only when the generation changes).
- A non-terminal plugin pane has no entry in `tab.terminals`; `render_split` currently draws a `<plugin> plugin`
  placeholder for it, to be replaced by the pane views.
- Log lines arrive from threads: a 300 ms ticker redraws the workspace while any tail runs.

Pane actions (all return at once; results redraw the workspace):
- `http_send(id, Request)`, `http_replay(id, exchange, times)`, `http_diff(id, a, b)`, `http_select(id,
  Option<u64>)`.
- `sql_run(id, pane: Option<PaneId>, query)`, `sql_request_write(id, pane: Option<PaneId>, statement)` (posts a
  gate; `write_pending` shows until it is approved or rejected).
- `browser_open(id, url_or_path)`, `browser_reload(id)` (both start Chrome when needed).
- `logs_clear(id, pane)`.
